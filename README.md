# qa-metrics-analyzer

Збір метрик якості з трекера (**Azure DevOps** або **Jira**) і **GitHub**, оцінка
придатності даних, обчислення бази метрик і **діагностичний звіт за комбінаціями
метрик**, а не за окремими числами.

Інструмент побудований під припущення «я не знаю цього проєкту»: він спершу
вимірює, чи можна взагалі вірити даним, і лише потім рахує метрики — а ті, що
порахувати не можна, показує як **явні сліпі зони**, а не мовчить про них.

## 1. Вхідні параметри

| Джерело входу | Що задає | Обов'язково |
|---|---|---|
| `config/profile.json` | Профіль проєкту (D7): трекер, репозиторій, період, вікно W, **версії кожної формули**, правила `Env` / `Imp` / резолюцій, список обов'язкових полів, пороги, релізи, спринти | так |
| `.env` | Креденшели: `ADO_PAT`, або `JIRA_EMAIL` + `JIRA_API_TOKEN` + `JIRA_FIELD_MAP`, і `GITHUB_TOKEN` | так (крім `fixture`) |
| CLI-прапорці | `--profile <path>`, `--run <runId>`, `--out <dir>` | ні |
| `config/risk-register.json` | Реєстр ризиків (likelihood × impact) і список вимог → Q4, Q5, G1, G2 | ні |
| `config/gate-decision.json` | Рішення про реліз і залишкові ризики з підписом → Q8, G9, G10 | ні |
| `config/cost-model.json` | PAF-модель витрат → Q17 | ні |
| `qa-runs/*.json` | Підсумки прогонів від репортерів Playwright / Cypress → Q16 | ні |

### Ключові поля профілю

```jsonc
"versions": {
  "tDet": "v2",          // v1 найраніше спостереження | v2 Created Date
  "env":  "v2",          // v1 поле середовища | v2 тег | v3 автор | v4 ключові слова
  "imp":  "v2",          // v1 Severity | v2 Priority на момент triage | v3 поточний Priority
  "module": "v2",        // v1 мапа за файлами | v2 Component/AreaPath | v3 команда
  "cohort": "v2",        // M1: v1 Version detected/спринт | v2 дата | v3 Version corrected
  "completeness": "v1"   // D4.1: v1 змінено від дефолту | v2 != дефолт | v3 непорожнє
}
```

Версія — це не налаштування «як зручніше». Це запис того, **наскільки слабкі ваші
дані**, і він друкується в кожному звіті. `env.closedWorld: true` («немає сигналу
— значить не прод») окремо позначається як найризикованіше припущення в усьому
пайплайні.

### Як будується URL до Azure DevOps

Кожен виклик ADO має вигляд `{collection}/{project}/_apis/...`. Різниця лише в
тому, де закінчується collection:

| Середовище | collection |
|---|---|
| хмара | `https://dev.azure.com/{organization}` |
| on-prem | `https://tfs.company.local/tfs/{collection}` — окремої organization немає |

Тому `baseUrl` — єдине джерело істини, а `organization` необов'язкова: вона
дописується тільки якщо `baseUrl` нею ще не закінчується. Всі чотири варіанти
нижче дають однаковий результат, і вставлений цілком URL організації більше не
породжує `/org/org/`:

```jsonc
{ "baseUrl": "https://dev.azure.com",       "organization": "ecohz" }
{ "baseUrl": "https://dev.azure.com/ecohz", "organization": "ecohz" }
{ "baseUrl": "https://dev.azure.com/ecohz" }
{ "organization": "https://dev.azure.com/ecohz" }                  // org як повний URL
{ "baseUrl": "https://tfs.company.local/tfs/DefaultCollection" }   // on-prem
```

Назва проєкту проходить через `encodeURIComponent` — пробіли в назвах
трапляються частіше, ніж хочеться. Побудований endpoint друкується в нотатках збору (`Project endpoint: ...`).

**Тіло помилки включається в текст винятку**, а не тільки статус. ADO відповідає
на 4xx JSON-ом із полем `message`, де названа справжня причина: неправильна
назва проєкту, бракує scope у PAT, WIQL перевищив ліміт у 20 000 записів. Сам по
собі `404 Not Found` відправляє дебажити не те. Те саме зроблено для Jira
(виняток) і для GitHub та Azure Pipelines (нотатка в звіті, бо вони деградують,
а не падають).

### Перемикання трекера

```jsonc
"tracker": { "kind": "azure-devops", "organization": "org", "project": "Proj" }
"tracker": { "kind": "jira", "baseUrl": "https://x.atlassian.net", "project": "PROJ" }
"tracker": { "kind": "fixture" }   // синтетичні дані, працює без креденшелів
```

### Джерело коду: локальний клон або GitHub API

```jsonc
"vcs": { "kind": "local-git", "path": "/шлях/до/клона", "branch": "master" }  // рекомендовано
"vcs": { "kind": "github", "owner": "org", "repo": "repo", "branch": "master" }
"vcs": { "kind": "none" }
```

Локальний клон кращий за API з трьох причин: один процес `git log` замість
одного HTTP-запиту на кожен коміт (GitHub-адаптер обрізає історію на 800
комітах і каже про це в нотатках), немає rate limit, і код не залишає вашу
машину. Це також **єдине** джерело, на якому потім працюватиме SZZ — `git blame`
по історії неможливий через API.

Шлях можна не тримати в профілі: `REPO_PATH` у `.env` перекриває `vcs.path`,
щоб профіль лишався портабельним між машинами.

Що адаптер робить правильно, і чому це не дрібниці:

| Випадок | Обробка | Що було б інакше |
|---|---|---|
| Перейменування (`src/{billing => payments}/pay.ts`) | береться шлях призначення | перейменування виглядало б як фантомний hotspot |
| Merge-коміти | виключені (`--no-merges`) | подвійний облік рядків гілки, роздутий churn |
| Бінарні файли | 0 рядків, кількість у нотатках | `NaN` у churn |
| Shallow clone | попередження в нотатках звіту | обрізана історія мовчки занижує density |
| `Merged PR 1234:` і `(#77)` | обидва формати | зв'язність дефект↔PR (Q3) впала б на ADO-репозиторіях |

### Перемикання джерела CI

```jsonc
"ci": { "kind": "azure-pipelines", "runSummaryDir": "qa-runs" }  // деплої з ADO, прогони з репортерів
"ci": { "kind": "json-file", "runSummaryDir": "qa-runs" }        // тільки прогони
"ci": { "kind": "none" }
```

Jira-інстанси мають різні id кастомних полів, тож мапа задається в `.env`:

```
JIRA_FIELD_MAP={"severity":"customfield_10030","rootCause":"customfield_10041","environment":"customfield_10052","sprint":"customfield_10020"}
```

## 2. Вихідні дані

| Артефакт | Шлях | Правило перезапису |
|---|---|---|
| Знімок сирих даних | `data/raw/<runId>/snapshot.json` | **незмінний**, повторний запис відхиляється |
| Звіт для людей | `data/reports/<runId>/report-<ISO-timestamp>.md` | **новий файл щоразу** |
| Звіт машинний | `data/reports/<runId>/report-<ISO-timestamp>.json` | **новий файл щоразу** |
| Журнал прогонів | `data/runs.jsonl` | тільки дозапис |

`runId` = `YYYYMMDDHHMMSS-<profile>-<hash>`. Перегенерація звіту з того самого
знімка створює новий файл, а старий лишається — це дає порівняння «до / після»
без зовнішньої системи версій.

### Структура звіту (R5)

1. Навіщо цей зріз
2. Що дані підтверджують — індикатори з фразою про точність
3. **Чого сказати не можна і чому** — сліпі зони з причиною
4. Діагноз — спрацьовані комбінації з рівнем впевненості
5. Сигнал проти шуму — XmR за правилами Wheeler
6. Максимум **три** пропозиції
7. Дата наступного зрізу

Далі — додатки: реєстр метрик, таблиця придатності даних (ISO/IEC 25012),
розбивки по кожній метриці, нотатки збору.

## 3. Запуск

```bash
npm install
npm run demo                      # синтетичні дані з навмисно закладеними проблемами

cp .env.example .env              # реальний проєкт
cp config/profile.example.json config/profile.json
npm run collect                   # тільки збір → знімок
npm run analyze                   # аналіз останнього знімка, без запису
npm run report                    # звіт з останнього знімка → новий файл
npm run run                       # collect + report
npm run typecheck
```

Розділення `collect` / `report` навмисне: збір коштує API-квоти й часу, звіт —
ні. Перегенерувати звіт після зміни порогів або версії формули можна скільки
завгодно разів на тому самому знімку.

## 4. Як це влаштовано

```
tracker/vcs/ci  →  Snapshot  →  Fitness (D4)  →  Normalize (M1,M2,Imp)
                                    ↓                   ↓
                                  Gate  ──────→  Metrics registry
                                                        ↓
                                          Indicators → Combination rules → Findings
                                                        ↓
                                                   XmR signals
                                                        ↓
                                                     Report
```

Порти й адаптери: `src/core` не знає нічого про ADO чи Jira. Додати трекер —
це один файл в `src/adapters/tracker`, який повертає `RawDefect`.

**Гейт придатності** — центральна ідея. Кожна метрика декларує, від яких полів і
джерел вона залежить. Якщо поле непридатне (повнота < 50%, домінантне значення
> 85%, або заповнюваність залежить від команди чи пріоритету — MAR/MNAR за
Rubin), метрика позначається `NOT COMPUTABLE` з причиною. Порахувати щось по 41%
заповненості й показати менеджменту — гірше, ніж не рахувати нічого.

**Комбінаційні правила** — таблиці з мануалу (Q1×обсяг, DDP×FD, Flaky×DDP,
Reopen×час фіксу, кластери×CFR, трасованість). Таблиці бінарні, а індикатор
трирівневий: значення посередині приводиться до найближчої сторони, але
висновок тоді знижується з `confirmed` до `hypothesis`. Комбінація — це
гіпотеза з планом перевірки, не вирок.

**XmR** відрізняє сигнал від шуму за трьома правилами Wheeler. Реакція на кожне
коливання — це tampering, і вона погіршує процес.

## 5. Що інструмент навмисно НЕ рахує

| Метрика | Чому |
|---|---|
| Q6 статус виконання тестів на рівні тест-кейсів | Потрібна прив'язка кожного тесту до релізу, а не агрегати пайплайну |
| Q11 надійність, Q12 перф і безпека | Потрібні моніторинг і SAST/DAST. Дешево додати, коли вони вже в пайплайні |
| SZZ / археологія коду (документ 03) | Передумова — зв'язність дефект↔PR ≥ 25% без зміщення. Інструмент цю передумову перевіряє (Q3) і блокує висновки, поки вона не виконана |

Ці рядки друкуються в секції 3 кожного звіту як прийнятий ризик, а не як
неформальний пропуск.

## 6. Класифікація падінь: SUT / TAS / inconclusive

`Q16` тримається на розрізненні, якого **не дає жоден CI API**: ADO Test API і
GitHub Actions повідомляють «failed» і все. Різницю знає тільки раннер.

`reporters/` містить:

| Файл | Що робить |
|---|---|
| `failure-class.ts` | Патерни TAS (мережа, впав браузер, хук, контейнер) і правило inconclusive |
| `playwright-qa-reporter.ts` | Рахує `expect`-кроки: зелений тест без жодного асерту → **inconclusive**, а не passed |
| `cypress-qa-plugin.ts` | Те саме через `command:end` + `after:run`; для Cypress число inconclusive — нижня межа |

Підключення Playwright:

```ts
// playwright.config.ts
reporters: [['./reporters/playwright-qa-reporter.ts', { outputDir: 'qa-runs' }]]
```

Патерни TAS — стартові. Силабус вимагає, щоб визначення були **явні й
послідовні**, а не розумні; тому список лежить під версією і калібрується на
ваших падіннях.
