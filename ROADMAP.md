# Поетапний план: що додаємо, коли і чому саме в цьому порядку

Порядок побудований за **ROI × ризиком**, а не за структурою мануалу. Мануал —
довідник; порядок впровадження в ньому не оптимізований під вартість підтримки.

Позначення: **[✓]** реалізовано · **[◐]** частково · **[ ]** заплановано.

---

## Фаза 0 — Каркас (реалізовано)

**[✓]** Порти й адаптери, домен-модель, профіль D7, незмінні знімки, журнал прогонів, CLI.

Чому першим: без профілю версій кожна наступна метрика буде порахована за
випадковим визначенням, і через три місяці ніхто не зможе сказати, чому число
змінилося — через продукт чи через формулу.

**Вартість підтримки:** одноразова. **Ризик пропуску:** усі подальші зрізи
непорівнянні між собою.

**ROI:** найвищий у проєкті. Один прогін відповідає на питання «які з ваших
одинадцяти питань я взагалі можу закрити».

значення, коли частка відкритих старших за ціль перевищить ~20%.

## Фаза 4 — CI і тест-набір (реалізовано)

**[✓]** Адаптер Azure Pipelines: деплої з Release API, прогони з Test API
**[✓]** `JsonFileCi` — читає підсумки прогонів від репортерів
**[✓]** `CompositeCi` — деплої з ADO, прогони з раннера (бо TAS знає тільки раннер)
**[✓]** Репортер Playwright з підрахунком `expect`-кроків → inconclusive
**[✓]** Плагін Cypress з підрахунком асертів через `command:end`
**[✓]** M4.7 regression cycles з деплоїв у тестове середовище
**[ ]** Q6 статус виконання на рівні тест-кейсів, прив'язаний до релізу
**[ ]** Адаптер GitHub Actions (потрібен лише якщо частина прогонів там)

**Чому це наступне:** flaky rate стоїть **першим** у порядку дій R3. Поки
червоне не читають, жоден інший сигнал CI не працює. Але без реального
адаптера ця метрика — просто число з fixture.

**Вартість підтримки:** середня. Формат тест-результатів змінюється рідше, ніж
схема трекера.

**Практичний крок у ваших фреймворках:** репортер, що пише
`{ status, failureClass: 'SUT' | 'TAS' | 'inconclusive', retryCount }` у JSON
поруч із прогоном. Без цього класифікація падінь лишається ручною вибіркою
30–50 записів на період.

## Фаза 5 — Ризик у коді (документ 03)

**[✓]** Адаптер `local-git`: `git log --numstat` з локального клона, обробка перейменувань, merge-комітів, бінарників і shallow-клонів
**[ ]** A2 лінкування дефект → BFC через `pullRequests` / `commits`
**[ ]** A3–A5 SZZ-lite: diff BFC, blame, фільтри, вибір BIC
**[ ]** A6 detection latency, медіана vs p90
**[ ]** A10 defect density на KLOC new & changed, hotspots
**[ ]** A12 ризик за розміром змін

**Передумова, яку інструмент уже перевіряє:** зв'язність дефект↔PR ≥ 25% без
суттєвого зміщення (Q3). Якщо зв'язність нижча, hotspots опишуть не ризиковий
код, а команду, яка акуратніше лінкує PR-и. Це помилка, яку неможливо
побачити в результаті — тільки в передумові.

**Вартість підтримки:** найвища в проєкті. Локальний клон уже є (`local-git`),
але лишаються git blame по історії, обробка рефакторингів і вибір BIC серед
кількох кандидатів. Тому фаза стоїть п'ятою, а не другою.

**Що дає:** відповідь на «де слабкий захист у коді» — Трійка 2 мануалу.

## Фаза 6 — Ручні входи як файли під версією (реалізовано)

**[✓]** `config/risk-register.json` → Q4, Q5
**[✓]** `config/gate-decision.json` → Q8, G9, G10
**[✓]** `config/cost-model.json` → Q17 з average saving per defect
**[✓]** Чекліст гейту G1–G10 як окрема метрика зі станом `NO DATA` на кожен рядок, який нічим не підтверджений
**[ ]** K6: метрики успішності RBT за шістьма питаннями TM 1.3.6

Чому не автоматизуємо: реєстр ризиків і рішення про реліз — це **рішення**, а не
вимір. Інструмент має перевіряти, що файл існує, заповнений і підписаний, а не
генерувати його.

**ROI:** високий і дешевий. Три JSON закривають чотири метрики бази і роблять
можливим гейт релізу. Ключова деталь реалізації: Q4 як головне число показує не
частку непротестованих ризиків, а частку **непротестованих і не прийнятих**.
Ризик з підписом — це рішення, а не порушення гейту, і плутати їх означає
карати команду за чесність.

## Фаза 7 — Поза трекером (документ 05), під гіпотезу

Запускається **тільки** коли базова метрика дала сигнал, не за розкладом:

| Симптом зі звіту | Що додаємо |
|---|---|
| DDP високий, але клієнти скаржаться | P1 звірка помилок у проді з трекером, P2 джерело виявлення |
| Тести є, а баги йдуть | P5 мутаційне тестування hotspots, P7 покриття змінених рядків |
| Одні й ті самі модулі ламаються | P9 аналітика code review, P10 ownership і truck factor |
| На staging працює, у проді ні | P12 паритет середовищ |

Не робимо це наперед. Кожна практика тут коштує днів роботи і має сенс лише
під конкретну гіпотезу з фази 3.

## Що НЕ буде реалізовано і чому

| Що | Причина відмови |
|---|---|
| M3 double sampling автоматично | Вимагає ручної розмітки вибірки. Автоматизувати можна тільки арифметику (Wilson-інтервали вже є), не саму розмітку |
| Дашборд у реальному часі | Мануал прямо називає це пасткою: презентувати дашборд замість рішень. Звіт має змінити хоча б одне рішення, інакше він не спрацював |
| LLM-класифікація root cause | Політика даних: внутрішні дані проєкту не йдуть у зовнішні API. Root Cause і так заповнюють розробники для P1/P2 |
| Метрики по людях | Дані про авторів лишаються тільки в агрегатах по модулях. Код і процес, а не люди |
